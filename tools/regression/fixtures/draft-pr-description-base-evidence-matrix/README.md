# Sanitized Fixture: Streamlined PR Description Evidence

This fixture models independent `draft-pr-description` shortcut runs.

## Current Worktree

- Direct Git reports a valid `terraform-provider-azurerm` feature branch while injected editor metadata names an older branch. The direct Git branch owns the no-argument run.
- One fixed direct-Git batch captures repository identity, full `HEAD`, porcelain status, and local main-ref candidates. A second fixed direct-Git batch captures the selected merge base, committed paths, working-tree paths, untracked paths, and commit subjects.
- Each Git batch uses the prompt's exact one-line semicolon-separated command string once. It is never attempted first with newline-separated commands or retried in alternate shell syntax.
- Terminal calls contain only the literal Git commands declared by the prompt. File reads use tool-native operations, and schema conformance is checked in memory without generated PowerShell or shell programs.
- No GitHub search, remote fetch, WSL discovery, or development-root scan runs.

## Stale Fork Base Recovery

- One fork has a stale local `origin/main`. Its initial merge-base scope includes incorporated provider commits across many service packages below a coherent contributor feature stack.
- The broad initial scope triggers one compact first-parent metadata call containing commit IDs, parents, author and committer identities, and subjects without per-commit patches.
- One candidate origin is derived from the clear contiguous contributor stack at `HEAD`. The fixed scope command runs once from that candidate parent.
- The recovered net scope is non-empty, strictly narrower, and contains one coherent primary service package with its generated, vendored, test, documentation, registration, Resource Identity, and List Resource companions. Drafting continues using only that recovered scope.
- A separate stale-base scenario has no clear contributor boundary. It retains the original scope without another recovery pass, then resolves coherence from material dependency evidence.

## Mainline Integration Merge Recovery

- One contributor starts `azurerm_example_project_connection` work, then merges a newer `upstream/main` snapshot and continues addressing review comments.
- The integrated mainline contains an unrelated `azurerm_example_account_connection` enhancement that the stale named base incorrectly exposes in the initial scope.
- First-parent metadata shows one newest clear two-parent merge with a subject that explicitly merges `upstream/main` into the feature branch.
- Recovery uses that merge's second parent as its only candidate origin. The one replacement scope contains contributor changes from both before and after the merge while excluding the incorporated account-connection enhancement.
- The accepted draft describes and recommends changelog entries only for `azurerm_example_project_connection`; it does not add an Enhancement classification or changelog line for `azurerm_example_account_connection`.
- A run without a clear mainline integration merge continues to use the linear oldest-contributor parent fallback. It never tests both candidate forms.

## Change Evidence

- One coherent run changes a Resource, matching tests, and matching documentation. Compact reads cover those surfaces and required registration only.
- The changed inventory names all owned files, so one concurrent Phase 2 batch reads the selected material files directly. It does not search for known paths, list the service directory, enumerate test functions, or stage implementation, test, and documentation reads across later rounds.
- One ordinary run changes a shared provider helper plus directly connected Resources in two service packages. Call sites, tests, documentation, and commit subjects establish one behavior intent, so drafting continues and preserves all user-facing surfaces.
- A separate ordinary run changes independent Resources with unrelated outcomes and no shared dependency evidence. It hard-stops after the evidence batch, regardless of whether those Resources live in the same or different service packages.
- Committed, staged, unstaged, and untracked paths remain visible in the complete inventory.

## Validation Claims

- Matching changed tests satisfy authored-test checklist wording.
- No test command runs during drafting, so every test-passed item remains unchecked and `Testing` says tests were not run during this invocation.

## Stability

- A stable run returns the same full `HEAD` and porcelain status immediately before rendering.
- A changed run returns a different value and hard-stops once without full-content fingerprinting or automatic restart.

## Execution Budget

- An ordinary run uses four primary phases, no more than 10 model iterations, and no more than 15 tool calls.
- Extra rounds are allowed only when one concrete missing fact blocks an accurate title or body.
- Stale-base recovery is that bounded exception: one metadata call and one replacement scope call at most.
